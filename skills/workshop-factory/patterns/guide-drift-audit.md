# Pattern: Guide-Drift Audit

For an **already-published** lab guide that's drifted out of sync with a live instance's UI — renamed buttons, moved navigation, redesigned features, ambiguous seed data — as opposed to `lab-guide-pipeline.md`, which covers authoring a **new** guide from a PDF. Validated end-to-end on `buildtheo/paitw`, 2026-07-21.

`/ice-package lab-guide`'s Phase 3 (step validation) already mechanizes a version of this — comparing markdown steps against a live instance and annotating corrections. Reach for that first if you're revalidating a guide wholesale. This pattern is for the narrower, more common case: you already have (or are handed) a **scoped findings doc** naming specific sections to fix, and the fix requires real judgment about *why* something drifted, not just relabeling a button.

## The loop

1. **Start from a findings doc, not a blank live-QA pass.** Separate confirmed-broken from suspected-but-unverified findings before touching any markdown — don't fix something the findings doc only guessed at without re-checking it yourself.
2. **Clone fresh, `git pull` first.** GitBook Git Sync pushes back into the repo automatically — a stale local clone will silently clobber content GitBook wrote back since your last pull.
3. **Re-verify nav-drift findings live, in parallel, one subagent per unrelated app area** (e.g. AI Agent Studio vs. Service Operations Workspace), rather than one serial session walking through everything. Roughly halves wall-clock. Each subagent needs the shadow-DOM technique notes restated in its prompt — see `~/.claude/skills/../reference` memory `reference_paitw_browse_technique_notes.md`; a fresh subagent has no memory of a prior session's hard-won workarounds.
4. **Don't trust a prior finding's *mechanism* claim at face value, even from the same day.** A same-day finding said a redesigned "Explore" panel let you type a natural-language filter "and Now Assist creates the filter for you" — sounds like a straight relabel of the old flow. One extra targeted verification agent found it's actually a **chat-style Q&A that answers inline and never touches the underlying list** — a materially different mechanism that would have shipped as a fresh doc bug if the rewrite had just transcribed the initial finding. Spend one extra live check whenever a rewrite's correctness hinges on *how* a redesigned feature behaves, not just what it's now called.
5. **Recapture screenshots as part of the same live pass**, not a deferred follow-up — save to scratchpad during verification, then copy into `.gitbook/assets/` with descriptive filenames once the surrounding text is finalized.
6. **Check for orphaned assets already sitting in `.gitbook/assets/` before assuming a missing step needs a fresh screenshot capture.** A doc gap ("step says 'select the file you just downloaded' but no download step exists") had its image already sitting unused in the assets folder — a leftover from a copy-paste gap in the original authoring, not something needing a new live capture.
7. **Clean up `/browse`'s own working-directory artifacts before staging.** Headless browsing sessions can drop `.gstack/` logs and stray files (audit logs, terminal tokens, one-off debug output) directly into the repo's working directory, not just the scratchpad — check `git status` for untracked junk before every `git add`, not just once at the start.
8. **Confirm the plan before pushing**, and get a repo-scoped write token explicitly — a token that works on a *different* repo owned by the same GitHub identity will still fail here; GitHub's rejection message distinguishes "wrong scope" (`invalid credentials` — token is valid, just lacks access) from "not a recognized token at all" (`Invalid username or token` — expired/revoked/malformed), which tells you which way to go back to the user.

## Why this matters more than it looks

The mechanism-level re-check (step 4) is the highest-leverage move in this pattern — it's the one place a naive "transcribe the findings doc into new prose" pass produces a *confident, plausible, wrong* rewrite instead of an honest "couldn't verify" flag. Everything else in this pattern is about not wasting the live-verification budget you do spend (parallelize, don't re-capture what already exists, don't let tooling artifacts contaminate the commit).

**How to apply:** Any time you're handed a lab-guide fix task that starts from a findings doc rather than "write a new guide from this PDF." See `~/.claude/skills/workshop-factory/patterns/lab-guide-pipeline.md` for the sibling "new guide" pipeline, and the `lab-guides-workflow` / `reference_paitw_browse_technique_notes` memories for the full session history and reusable shadow-DOM technique details.
