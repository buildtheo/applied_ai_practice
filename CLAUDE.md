# Applied AI Portfolio Maintenance

`applied-ai-portfolio.md` is the canonical source of truth for Theo Simmons's Applied AI work, projects, evidence, operating philosophy, leadership stories, and career positioning.

## Purpose

Maintain this document as a factual working reference for:

- resumes
- job applications
- interviews
- portfolio descriptions
- recruiter and hiring-manager conversations
- leadership narratives
- future candidate-coaching skills

The document is not marketing copy. It is an evidence base.

## Core rule

Never invent, infer, inflate, or silently improve a claim.

Only add information supported by one or more of the following:

1. Working code or project files
2. Test results or evaluation output
3. Deployment records
4. Written project notes
5. Approved resume content
6. Metrics supplied or confirmed by Theo
7. A direct statement from Theo

If evidence is incomplete, label the item:

- `UNVERIFIED`
- `NEEDS METRIC`
- `NEEDS CONTEXT`
- `NEEDS CONFIDENTIALITY REVIEW`

Do not convert an unverified statement into a factual resume claim.

## Voice

Preserve Theo's voice:

- direct
- concise
- operator-first
- evidence-driven
- comfortable naming the real problem
- simple language
- varied sentence rhythm
- Strunk-and-White bias

Prefer:

- what was built
- why it was built
- how it worked
- what was difficult
- what changed
- how the result was measured
- what was learned

Avoid:

- generic thought leadership
- buzzword stacks
- identical Action → Metric → Impact cadence in every entry
- polished thesis/conclusion structure
- excessive use of "strategic," "transformational," "innovative," "scalable," or "production-grade"
- making every sentence sound memorable
- language written mainly to satisfy an ATS
- prose that sounds more impressive but is less defensible

Preserve signature phrases only where they add real value:

- "I don't pitch what I can't build."
- "The hard part comes after the room gets excited."
- "I build real AI systems that ship, get measured, and get used."
- "I've spent two years running this motion solo. I want to run it with a team."
- "The model is rarely the hard part."
- "Capability is not deployment."

Do not repeat these phrases excessively.

## Evidence discipline

For every substantial project, maintain:

- Project name
- Status: concept / prototype / working tool / internal deployment / production
- Problem addressed
- User or intended user
- What Theo personally did
- Architecture and stack
- LLM role
- Deterministic or non-LLM components
- Tool and API interactions
- Trust boundaries and safety controls
- Evaluation method
- Measured results
- Scale or usage
- Hardest engineering or operating problem
- What was learned
- Claims safe for public use
- Claims restricted to internal use
- Claims requiring verification
- Last verified date

Distinguish clearly between:

- personally built
- led
- co-built
- influenced
- enabled
- evaluated
- proposed
- planned but not completed

## Risk register

Continuously check for these known risks:

### Seniority

Do not say "highest-ranking IC at ServiceNow."

Safe framing:
"Operates at a senior-most IC level within the Applied AI field organization."

### Current leadership

Current ServiceNow role is a senior IC/player-coach role unless Theo confirms direct reports.

Past formal leadership at Column includes a 100+ person organization and P&L responsibility. Keep current influence leadership and prior formal people management distinct.

### Production claims

Use "production-grade" only when the system is deployed, monitored, supported, and relied upon operationally.

Otherwise use:

- working system
- production-pattern
- production-ready pattern
- tested against live or production-like conditions

### Red-team language

Keep the finding sharp, but frame Theo as identifying the governance gap and helping close it.

Preferred:
"Led a red team validating how quickly a single engineer can route AI agents around enterprise workflow systems via direct APIs—informing where governance, trust boundaries, and operating controls need to be designed in up front."

### Cost and ROI

Do not use cost comparisons or projected ROI without preserving assumptions, calculation method, and whether the figure is measured, modeled, or projected.

### Confidentiality

Do not expose customer names, internal system details, sensitive architecture, unpublished roadmap information, or customer-specific findings unless Theo explicitly marks them public.

## Update workflow

When reviewing new work, resumes, project files, notes, or interview preparation:

1. Read the existing `applied-ai-portfolio.md`.
2. Identify genuinely new evidence.
3. Separate:
   - new fact
   - correction
   - stronger evidence for an existing claim
   - new interpretation
   - role-specific wording
4. Do not duplicate the same accomplishment under multiple names.
5. Update the canonical project or evidence entry.
6. Preserve previous factual context unless disproven.
7. Add the current date to the changelog.
8. Produce a review report before editing.

## Mandatory review report

Before changing `applied-ai-portfolio.md`, return:

### New evidence found

What is genuinely new.

### Existing entries affected

Which sections would change.

### Claims strengthened

What now has better proof.

### Risks or contradictions

Conflicts with prior claims, metrics, dates, ownership, status, or confidentiality.

### Proposed edits

Exact additions, replacements, or deletions.

### Voice check

Anything that sounds over-polished, generic, repetitive, or unlike Theo.

Wait for approval before modifying the canonical document.

## After approval

After Theo approves:

1. Apply only the approved edits.
2. Update `Last updated`.
3. Add a short changelog entry.
4. Do not rewrite unrelated sections.
5. Do not globally "improve" the prose.
6. Return a concise diff summary.

## Periodic audit

When asked to run a portfolio audit:

1. Check for duplicate projects or claims.
2. Find inconsistent metrics, dates, titles, and ownership language.
3. Find claims with no supporting evidence.
4. Identify stale project statuses.
5. Identify accomplishments appearing in resumes but missing from the portfolio.
6. Identify portfolio evidence not yet used effectively in any resume.
7. Flag passages with uniform AI-like rhythm or excessive polish.
8. Recommend updates, but do not apply them without approval.

## Resume learning loop

After every job application or resume-tailoring exercise, report:

- Which evidence mattered most for the JD
- Which projects gained or lost relevance
- Which claims drew scrutiny
- Which wording sounded authentic
- Which wording sounded over-optimized
- New likely interview probes
- Recommended portfolio updates
- Recommended resume-bank updates

Do not turn temporary JD language into permanent identity without Theo's approval.
